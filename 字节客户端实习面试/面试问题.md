# 闪亮实习生
### 1. 你如何设计一个面向海外的美妆/时尚/美食社区的首页 Feed 流？
> 在设计海外社区的首页 Feed 时，我会从**性能**、**多语言适配**、**合规**、和**内容策略**几个方面来考虑。  
> 首先是**分页策略**，会优先使用 **cursor-based** 分页，它相对于 offset 更适合动态更新的数据流，能保证数据的一致性。  
> 为了提升滑动体验，会做 **首屏预渲染和预加载**，比如提前加载下一屏内容或首屏骨架屏。

在国际化方面，需要支持 **多语言切换**和**时区展示**，比如帖子发布时间应显示为用户本地时间。内容审核也要考虑合规，比如 GDPR 要求对敏感内容的处理，以及关键词屏蔽等。

此外，Feed 中会预留 **A/B 实验位**，比如新推荐算法或新组件验证效果。我们也会接入埋点体系，埋点包括：**曝光、点击、停留时长等行为**，为后续优化推荐和排序提供数据支持。
### 2. 如果让你做「内容种草 → 商品成交」的链路，客户端需要埋哪些关键事件？
> 从种草到成交，这条链路我会埋四类核心事件：

- **viewContent**：用户浏览种草内容的曝光事件；
    
- **addToWishlist**：用户收藏商品或加入心愿单行为；
    
- **clickProduct**：点击跳转到商品页或外部电商平台；
    
- **purchase**：最终成交行为，比如下单成功或跳转后的回传。
    

为了保持埋点的**一致性和扩展性**，我会把这套事件封装成一个 **统一的 Tracking SDK**，通过事件名+参数上报，支持动态配置和灰度发布。

此外要注意合规，尤其在欧洲或加州等地区，要处理 **GDPR/CCPA** 的 opt-in 同意机制，比如用户拒绝 Cookie 收集时，相关追踪就需要禁用。
### 3. 如何提升海外用户的次日留存？
> 提升次日留存我会从**通知策略**、**首日体验**、和**社交互动**几个方面入手。  
> 首先是 **Push 推送合规**，确保接入 FCM（Android）和 APNs（iOS）后做权限申请优化，同时考虑 **本地时间的推送调度**，比如早上 9 点是用户最容易接收内容的时段。

冷启动方面，我会优化首帧加载，尽量把冷启动控制在 **1.5s 以内**，比如使用骨架屏、懒加载资源、按需初始化 SDK。

在内容方面，可以做 **新用户引导 A/B 测试**，对比「故事流」和「左右滑动」模式哪个更能激发探索欲望。  
最后，引导用户进行 **社交关注**也很关键，比如「你可能认识的人」「关注达人账号」能形成社交粘性，提升次日回访率。
### 4. 说说 ViewModel + LiveData 在 MVVM 架构里的作用，如何避免内存泄漏？
> 在 MVVM 架构中，**ViewModel** 主要负责业务逻辑与数据处理，**LiveData** 是数据的响应式桥梁，它具有生命周期感知能力，能自动绑定和解绑观察者。

ViewModel 本身是绑定在 **Activity 或 Fragment 的生命周期之外**的，它不会持有 UI 组件引用，因此可以有效避免因配置变更导致的重复创建或内存泄漏。

为了进一步避免泄漏，我会注意 **不在 ViewModel 中持有 Context 引用**，如果有需要，会使用 **ApplicationContext** 替代。同时，也避免 LiveData 被外部直接修改，只提供不可变的接口给 UI 层。
### 5. SwiftUI vs UIKit，你选哪个？为什么？
> 如果是新项目开发，我更倾向于用 **SwiftUI**，它是声明式的 UI 框架，代码更简洁，并且可以一套代码适配 **iOS、macOS、watchOS** 等多个 Apple 平台。  
> 但是 SwiftUI 在一些复杂交互场景或者低版本设备兼容性上，还有不如 UIKit 稳定的地方。

所以我会选择 **混合开发**：比如新增功能用 SwiftUI 快速上线，老功能或核心模块继续使用 UIKit，逐步迁移。这样可以兼顾开发效率和系统稳定性。
### 6. 跨端（Flutter/React Native）：如何与原生模块通信？
> 在跨端框架中，和原生通信是常见问题。  
> 比如在 Flutter 中会用 **MethodChannel**，在 React Native 中则用 **Native Module 或 TurboModule**。  
> 它们底层都是通过桥接机制调用原生代码。

通信中需要注意：

- **类型映射**：比如 Dart 和 Java/Kotlin 之间的 JSON、List、Map 类型转换；
    
- **线程模型**：UI 线程 vs IO 线程调度，防止卡顿；
    
- **包大小增量**：引入原生库时尽量模块化、按需加载，避免膨胀。
### 7. 给你 10 万张图片的 URL，如何快速去重？
> 如果只是按 URL 去重，可以用 **HashSet** 来去重，效率高，但内存占用大。  
> 如果内存受限，可以使用 **BloomFilter** 做概率性去重，占用空间小但有一定误判率。

当数据特别大时，比如百万级，我们可以把 URL 做哈希后按分片存到磁盘或 Redis，采用分布式 MapReduce 模式处理。  
这样整体的空间复杂度能从 O(n) 优化到 O(1)，也更适合离线批处理。
### 8. 冷启动优化做过哪些？
> 冷启动优化主要关注 **T0 到 T1 的全过程**，我会把启动过程拆成几步分析：

1. Application 初始化时间；
    
2. 首个 Activity 加载时间；
    
3. 网络请求或磁盘 IO 时间。
    

我会接入 Androidx Startup 或 iOS 的 +load 方法进行初始化调度，将耗时模块异步加载；并使用骨架屏提前占位，实现预加载。  
同时使用 trace 工具分析关键路径，比如 Firebase Performance、Android systrace，定位哪个模块耗时最长。
### 9. 如何做卡顿监控？
> Android 上可以使用 **Choreographer.FrameCallback** 检测每帧耗时，超过 16ms 就可能是卡顿。  
> iOS 上则用 **CADisplayLink 结合 RunLoopObserver** 监听主线程卡顿。

我们会收集卡顿堆栈，并进行**聚合分析**，然后通过符号化（symbolicate）恢复人类可读的函数调用链，最终用火焰图或者可视化工具定位最常出现的卡顿函数。
### 10. 网络层：弱网/跨国链路如何优化？
> 弱网环境优化我会从几个方面入手：

1. 协议层面升级到 **HTTP/3 或 QUIC**，减少握手开销；
    
2. 使用 **CDN** 部署海外节点，把内容推送到离用户更近的位置；
    
3. 多码率图片或视频做 **自适应加载**，节省带宽；
    
4. 对大文件或视频使用 **断点续传机制**；
    
5. 提前做 **DNS 预解析和连接预热**，降低首次请求的延迟。
### 11. 组件化：怎样防止模块间循环依赖？
> 防止循环依赖的关键是明确分层架构：比如将项目分为 **基础层、中间层、业务层**。  
> 每一层只能向下依赖，不能向上。

模块之间如果有调用关系，会通过接口抽象 + Router 实现，例如使用 **ARouter 或自定义 Navigator 模块**来做解耦。  
在 CI 阶段我也会加入 **依赖检查脚本**，一旦出现循环依赖就中断构建，防止隐性错误。

> 我倾向于在项目初期做一次完整的 **PRD 评审和技术风险评估**，提前发现接口不清晰或边界场景缺失的问题。

### 14. 对国际化社区的理解？和国内社区最大差异？
> 国际化社区面临的最大挑战是 **文化和合规的差异**。  
> 比如阿拉伯语国家要支持 **RTL 方向布局**，有些国家对颜色、图标含义有特殊禁忌。我们需要做足本地化适配工作。

在隐私层面，必须合规处理用户数据，例如 **GDPR、CCPA、未成年人隐私保护**等都对埋点和数据采集提出了严格限制。
此外，商品链路的**支付方式、物流路径、货币单位**也和国内完全不同，需要和产品团队一起做好链路梳理，避免用户中途流失。

### 2. 当面对客户端开发技术难题时，你通常会通过哪些渠道获取解决方案？
首先，我会**优先查看官方文档和源码**。不管是 Android 的 Jetpack、iOS 的 SwiftUI 框架，还是三方库，我都习惯先回到最权威的信息源找线索，因为它不仅能解释 API 的使用方式，还会有一些注意事项、性能建议。

其次，我会在**技术社区和开发者论坛**查找类似问题，比如 Stack Overflow、掘金、Github issue 区或者 Reddit 等。遇到性能瓶颈问题时，我也会去看专业博客或者技术方案总结，比如「腾讯移动架构」或「Google Dev Blog」的最佳实践。

有时问题比较复杂，我会借助工具进行定位。比如遇到页面卡顿或内存异常时，我会使用 **Android 的 Systrace或 iOS 的 Instruments** 进行性能分析，先找到瓶颈点再去做优化。

如果这些还无法解决，我会**主动请教更有经验的老师、同学**或社区里的开发者。
### 3. 请说明在客户端开发中，如何保障用户输入数据的合法性和安全性？

> 在客户端开发中，我会先在前端做基础的输入校验，比如判空、长度限制、特殊字符过滤，防止用户误输或者简单的恶意输入。  
> 同时，我们使用 HTTPS 保证传输过程安全，登录注册场景下还会用验证码、防重复点击等手段来防止刷接口。

用户身份这块，我j通常会用 JWT 或 Session 做登录状态的维护，并定期刷新 token 防止被盗用。  
对一些关键接口，比如评论、搜索等，我会限制频率和内容长度，避免刷评论或注入攻击。
另外，我也会定期更新依赖库、检查安全漏洞，保持代码和依赖的安全性。
### 4. 你如何理解客户端开发中响应式设计（Responsive Design），以及你如何在项目中应用？
响应式设计就是指页面或者应用可以**自适应不同设备尺寸和分辨率**，在客户端开发中，它的核心目标是确保不管用户用的是大屏手机、平板，还是小屏设备，界面都能正常显示，交互体验一致。
> 在实际开发中，我会从几个方面做响应式设计：

1. 使用**约束布局或自动适配方案**，保证不同分辨率下元素位置和尺寸合理；
2. 配合**尺寸单位和最小宽度限定符**来做资源适配；
3. 对图片资源使用不同分辨率的切图，并在必要时用**矢量图**减少模糊问题；
4. 结合媒体查询，如 CSS 中 media query，或系统 API 判断屏幕尺寸，动态调整布局/隐藏不必要的内容。
